# Поведение

**Спрашивай, а не додумывай.** Если задача неоднозначна, есть несколько подходов, затрагивается публичный CLI/формат вывода или непонятно что именно менять - спроси перед тем как писать код.

Перед каждым ответом перепроверяй код, логику и факты. Если не уверен - скажи прямо. Точность важнее скорости.

# Проект

phew - CLI-форматтер на Rust (2024 edition) для PHP/HTML view-файлов Yii 2. Парсит смешанный HTML + PHP в единое AST и переформатирует. Свой репозиторий (не форк фреймворка).

## Структура

- `src/` - parser (lexer, ast), formatter (engine, indent, split, echo, docblock, php), io, config
- `tests/fixtures/` - пары `input/` → `expected/`
- `bin/` - вспомогательные скрипты (`check-fixtures`, `diff-all`)

# Git

## Remotes и ветки

- Один remote: `origin` - `WarLikeLaux/phew` (сюда трекают ветки).
- `dev` - рабочая ветка, `main` - стабильная. PR идёт `dev` → `main`.

## Push

**НЕ пушить. Пользователь пушит сам.** Никогда не запускай `git push` (даже после коммита).

## ЗАПРЕЩЕНО

- `git commit --amend` - НИКОГДА (делает force push обязательным).
- `git rebase` на уже запушенных ветках - НИКОГДА.
- `Co-Authored-By` trailer - НИКОГДА, ни в каком виде.

Если нужно исправить коммит - делай НОВЫЙ. `git reset --soft HEAD~1` МОЖНО, если коммит ещё не запушен и нарушает правила.

## Коммиты

**Коммить без подтверждения** - когда нужно сохранить изменения, делай сразу, не спрашивай «закоммитить?».

- Формат: imperative mood, заголовок ≤ 72 символа, без точки. Имена файлов/функций/типов - в бэктиках.
- Без префиксов conventional commits (НЕ `feat:`, `fix:`).
- **ID задачи** (`Fix #N: ...`) - только на ПЕРВЫЙ коммит ветки (проверка: `git log --oneline main..HEAD` пусто = первый). Все остальные коммиты - БЕЗ id, просто imperative.
- Коммить только релевантные файлы (`git add <конкретные>`), не `git add .`. В рабочем дереве могут лежать чужие незакоммиченные правки - не вмешивать их в свой коммит.

## issue/PR

- `gh` авторизован - читай issue/PR через него: `gh issue view N --repo WarLikeLaux/phew --json title,body,comments`, `gh pr view N`.
- **WebFetch не видит комментарии GitHub** (рендерятся динамически) - для комментариев и ревью только `gh`.

# Инструменты

`just` (task runner) + `cargo`. Ключевые команды:

```bash
just check      # lint + test + fixtures - полная проверка перед коммитом
just dev        # fmt + lint (clippy -D warnings)
just test       # cargo test (юнит-тесты)
just fixtures   # ./bin/check-fixtures (пары input → expected)
just fix <args> # форматирование с записью (cargo run -- -w)
just run <args> # запуск форматтера
just d [chars]  # git diff с разбиением на части
```

CLI самого `phew`: `phew <path>` (stdout), `phew -w` (write-back), `phew --tokens`, `phew --tree`. `fix`/`check` и т.п. - это рецепты justfile, не команды бинарника.

# Тесты

- Юнит-тесты по модулям: `just test`.
- Фикстуры: пары `tests/fixtures/input/NN_name.ext` → `tests/fixtures/expected/NN_name.ext`. Проверка - `just fixtures`.
- **Доказательство фикса:** добавь фикстуру, которая БЕЗ правки падает, а С правкой проходит. Прогон до/после - доказательство, что тест ловит регрессию.
- Идемпотентность: повторный прогон форматтера не должен менять уже отформатированный файл.
- Перед написанием тестов и после - вызывай `/review-tests` (чеклист требований).

# Линтеры

- `cargo clippy -- -D warnings` (через `just lint`) - ноль предупреждений.
- `cargo fmt` (через `just fmt`) - перед коммитом код отформатирован.
- `just dev` гоняет оба разом.

# Версия

Бамп версии - только через `/release` (обновляет `Cargo.toml` + бейджи README за один проход). Не править версию вручную вразнобой.

# Скретч-файлы

`pr.md` в корне - временный текст PR (см. `/pr`), НЕ трекается git и НЕ коммитится. Перед затиранием чужого содержимого - спроси.

# Воркфлоу

Коммиты, ветки, PR-текст, ревью тестов - через скиллы (Skill tool), не вручную.

1. Обсуждаем задачу.
2. `/branch` - создать ветку и приступить (если задача того требует).
3. `/review-tests` - загрузить чеклист до написания тестов.
4. Пишу код + фикстуры; доказываю фикс прогоном С и БЕЗ него.
5. `/review-tests` - проверить написанное.
6. `just check` - зелёное.
7. `/pr` → текст в `pr.md` (НЕ вызывает `gh pr create`).
8. `/pr-bundle` - собрать `pr-bundle.md` для внешнего ревью.
9. Коммит - сразу, без вопроса, в нужном формате. **Push - не делать**, пользователь сам.

`gh pr create` - только по явной просьбе.

# Ответы на ревью PR

Когда пользователь присылает комментарий ревьюера (или CodeRabbit): проверь по текущему коду, валиден ли он. Тривиальный нитпик с идентичным поведением - проще внести, чем спорить. Реальное замечание - исправить + по возможности фикстура. Невалидное - кратко обосновать отказ. Для разбора и черновика ответа - `/reply`.

# Запрещено в любом тексте

**ИИ-слова:** comprehensive, robust, enhance, leverage, utilize, ensure, streamline, facilitate, plays a key role, significant impact

**Псевдо-контраст:** "It's not about X, it's about Y", "This goes beyond X", "At a deeper level"

**Универсальные обобщения:** "In today's world", "Now more than ever", "Many developers face"

**Логические склейки:** "In other words", "Thus", "Consequently", "On the one hand... on the other hand", "It's important to note"

**Мотивационные финалки:** "The key takeaway is", "In conclusion", "Let's dive in", "Let's break it down"

**Перестраховка:** "depending on the situation", "individual circumstances may vary"

**Повтор мысли разными словами:** написал тезис - не перефразируй его ещё раз

**Форматирование:**
- Длинные тире - использовать короткие (-)
- Восклицания и эмоции
- Пассивный залог без необходимости
- Идеально симметричные списки из 3-5 пунктов одинаковой длины

После написания любого текста (PR, комментарии, документация) вызывай `/humanize` для вычистки AI-slop.
